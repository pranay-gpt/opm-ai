## Module Descriptions

### 1. `opm_ai.chat` -  Web Interface
- **Purpose**: Main user interface built with React
- **Components**:
  - Sidebar navigation for selecting function (Chat, Results, Deck Builder, Run Simulation, Explain, Settings)
  - Chat interface with streaming LLM responses
  - Deck builder with syntax highlighting
  - Results viewer with KPIs and interactive plots
  - Settings panel for API keys and configuration
- **Key Features**:
  - Theme switching (Dark Void, etc.)
  - Provider selection (Groq, NVIDIA NIM, OpenAI etc)
  - Context-aware panels based on selected function

### 2. `opm_ai.builder` - Natural Language to Deck Conversion
- **Purpose**: Converts plain-English reservoir descriptions into executable OPM deck files
- **Three-stage pipeline**:
  1. **LLM Extraction**: Uses Groq to parse description into structured `ReservoirDescription` dataclass and using fixed data (SPE1, SPE9 etc) make .DATA (high accuracy required). Final linter will not use LLM for correction. Need to extract information form manual and preset database as guides.
  2. **PVT Calculation**: Computes fluid properties using preset database empirical correlations via `resdata`/`resfo`. Ask user option if multiple coorelation available.
  3. **Template Rendering**: Uses Jinja2 to populate `base.j2` template with reservoir data
- **Integration**: Automatically runs the linter on generated decks
- **Key Classes**:
  - `ReservoirDescription`, `WellSpec`, `FluidSystem` (data models)
  - `build_deck()`: Main public API
  - `_llm_extract_parameters()`: LLM-powered parsing
  - `_populate_pvt()`: PVT property calculation
  - `_render_template()`: Jinja2 rendering

### 3. `opm_ai.linter` - AI-Powered Deck Validation
- **Purpose**: Validates OPM decks and provides human-readable feedback
- **Two-stage pipeline**:
  1. **Static Rule Engine**: Fast, offline validation using predefined rules (1st priority, will generate most deck using this and reference dataset)
  2. **LLM Enhancement** (Optional): Adds plain-English explanations and fix suggestions via Groq
- **Output**: `LintResult` containing:
  - List of `DeckDiagnostic` objects (keyword, severity, message)
  - Boolean `is_runnable` flag
  - Optional LLM-generated summary (comment at top of deck)
- **Key Features**:
  - Works offline without API key (rule engine only)
  - Provides actionable feedback for fixing deck errors
  - Integrates with builder and runner modules

### 4. `opm_ai.runner` - OPM Flow Execution Engine
- **Purpose**: Executes OPM Flow simulations and captures results
- **Key Responsibilities**:
  - Locates OPM Flow binary (configurable via environment)
  - Builds command-line arguments (note: omits `--threads` flag due to compatibility issues)
  - Runs subprocess with timeout handling
  - Parses OPM output for errors and warnings
  - Locates output files (`.SMSPEC`, `.UNRST`)
  - Returns structured `SimulationResult`
- **Data Models**:
  - `SimulationJob`: Input parameters (deck path, timeout, etc.)
  - `SimulationResult`: Output status, files, timing, crash reports
  - `CrashReport`: Parsed OPM error/warning messages

### 5. `opm_ai.preprocess` - PVT and Property Generation
- **Purpose**: Computes fluid properties and rock properties for reservoir simulation
- **Key Components**:
  - `pvt_builder.py`: Calculates PVT tables from empirical correlations
  - Uses `resdata` and `resfo` libraries for OPM-compatible output formats
  - Handles oil-water and oil-water-gas fluid systems
  - Considers input parameters: API gravity, gas specific gravity, salinity, temperature, pressure
- **Integration**: Called by builder during deck generation

### 6. `opm_ai.postprocess` - Results Processing and Visualization
- **Purpose**: Extracts insights from simulation results and generates visualizations
- **Key Components**:
  - `resinsight_bridge.py`: Interface to ResInsight via `rips` Python API
  - `kpi_extractor.py`: Calculates key performance indicators (oil rate, water cut, GOR, etc.)
  - `plot_engine.py`: Creates interactive Plotly charts for production profiles, pressure maps, etc.
- **Integration**: Consumes output from runner and feeds results to UI

### 7. `opm_ai.explainer` - Educational RAG System
- **Purpose**: Provides educational explanations of simulation concepts and results
- **Status**: Planned (not yet implemented as of current codebase)
- **Planned Approach**:
  - Retrieval-Augmented Generation (RAG) pipeline
  - Vector database for petroleum engineering knowledge base
  - LLM-generated explanations with citations to textbook material
  - Context-aware questioning based on simulation results

### 8. `opm_ai.settings` - Configuration Management
- **Purpose**: Handles application configuration and environment variables
- **Managed Settings**:
  - LLM API keys (GROQ_API_KEY, NVIDIA_NIM_API)
  - OPM Flow binary path
  - Default models and parameters
  - UI themes and preferences

## Data Flow

### Typical User Workflow: Chat → Deck Builder → Simulation → Results

1. **User Input**: User types a reservoir description in the chat interface
2. **LLM Routing**: Request sent to LLM router which selects appropriate provider
3. **Deck Building**:
   - Description sent to builder module
   - LLM extracts reservoir parameters (dimensions, fluids, wells, etc.)
   - PVT properties calculated using empirical correlations
   - Jinja2 template generates OPM deck file
   - Deck automatically linted for validity
4. **Simulation Execution**:
   - Validated deck passed to runner module
   - OPM Flow executed as subprocess
   - Output parsed for errors/warnings and file locations
5. **Result Processing**:
   - Output files processed by postprocess module
   - KPIs extracted and plots generated
   - Results sent back to UI for display
6. **Optional Explanation**: User can ask "why" questions to trigger explainer module (planned)

- **Linter Only**: User can paste existing deck into linter for validation
- **Simulation Only**: User can provide deck file directly to runner (give browse button for loading user deck)

## Design Decisions and Patterns

### 1. Modular Architecture
- **Separation of Concerns**: Each major function (building, linting, running, explaining) is encapsulated in its own module
- **Loose Coupling**: Modules communicate through well-defined data structures (Pydantic models, dataclasses)
- **High Cohesion**: Each module has a single responsibility

### 2. Pipeline-Based Processing
- **Builder**: Multi-stage pipeline (LLM data extraction from description → RUNSPEC → GRID → PROPS & PVT calculation → REGIONS → SOLUTION → SUMMARY → SCHEDULE → putting of deck together)
- **Linter**: Two-stage pipeline (static rules → LLM enhancement)
- This approach allows for independent development and testing of each stage

### 3. Fault Tolerance
- **Graceful Degradation**: Linter can operate offline using only rule engine
- **Error Containment**: Runner never raises exceptions; returns structured error objects
- **Fallback Mechanisms**: Builder has default parameter generation when LLM unavailable

### 4. Extensibility
- **Provider Abstraction**: LLM router allows easy addition of new LLM providers
- **Template System**: Jinja2 templates enable easy modification of deck format
- **Plugin-Ready**: Clear module boundaries facilitate adding new capabilities

### 5. Educational Focus
- **Chat-First Interface**: Natural language interaction lowers barrier to entry
- **Planned Explainer**: RAG system will provide educational context
- **Visual Results**: Integration with ResInsight provides intuitive 3D visualization
- **Immediate Feedback**: Real-time linting helps users learn correct syntax

1. General OPM Flow calling rules
OPM Flow is designed to run Eclipse-style reservoir simulation decks (e.g. black-oil, compositional) via the flow executable.[darts.citg.tudelft]
1.1 Basic command-line pattern
•	Single-processor run, default settings:
flow CASE.DATA
where CASE.DATA is the Eclipse input deck (RUNSPEC, GRID, PROPS, REGIONS, SOLUTION, SUMMARY, SCHEDULE).[pkirkham.github]
•	With explicit output directory and restart handling (typical safe pattern):
flow CASE.DATA --output-dir=RESULTS_CASE --enable-num-threads=8
The manual documents all flags; common ones include output directory, thread count, restart handling, and verbosity.[opm-project]
•	MPI / parallel run:
mpirun -np N flow CASE.DATA
where N is number of MPI processes; use threads per process via --enable-num-threads to tune performance.[resinsight]
1.2 Deck compatibility & cleaning rules
Official guidance for running Eclipse models on Flow:[opm-project]
•	Only keywords supported by OPM Flow (as listed in the reference manual) will run; unsupported keywords must be removed or replaced with equivalent supported functionality.
•	Use decks from opm-data and opm-tests as reference for supported syntax and keyword combinations.
•	For older Eclipse decks, systematically:
o	Strip unsupported options (e.g. rare vendor-specific keywords).
o	Convert schedule controls to the supported set (WCONPROD, WCONINJE, etc.).
o	Ensure units and phases line up with Flow’s RUNSPEC expectations (METRIC, FIELD, SI).[darts.citg.tudelft]
 
2. Rules per drive mechanism & deck “type”
Flow does not have explicit “drive mechanism modes”; instead, the mechanism is encoded in RUNSPEC + PROPS + SCHEDULE. The way you call Flow is the same, but your validation plots and keywords differ.
2.1 Depletion / solution gas drive (OIL + dissolved gas)
Typical Eclipse deck: SPE1/SPE3-style black-oil case.[pkirkham.github]
•	RUNSPEC: OIL, GAS, kids of black-oil keywords; no aquifer or water influx.
•	PROPS: Standard PVT (PVTO, PVDG, PVTW) and relperm without aquifer functions.
•	SCHEDULE: Producers with BHP or rate controls; no injectors.
Calling Flow:
•	flow SPE3CASE1.DATA (single-core test).[pkirkham.github]
•	For performance runs: mpirun -np 8 flow SPE3CASE1.DATA with --enable-num-threads as needed.[resinsight]
Deck rules:
•	Make sure SUMMARY section requests primary depletion diagnostics (GOR, BHP, FOPT, FGPT, reservoir pressure).
•	Avoid compositional-only keywords; stick to the black-oil subset documented in the Flow manual.[opm-project]
2.2 Gas-cap drive (OIL + gas cap)
Similar black-oil deck but with initial gas cap and appropriate relperm tables.[darts.citg.tudelft]
Deck rules:
•	RUNSPEC includes both oil and gas phases; initial conditions specify gas cap region.
•	PROPS: Relperm curves must reflect gas cap behavior; gravity terms usually active.
•	SCHEDULE: Gas production and pressure maintenance must be consistent; BHP controls chosen to keep gas cap realistic.
Calling Flow:
•	Same as depletion: flow CASE.DATA or mpirun -np N flow CASE.DATA.[darts.citg.tudelft]
•	Summary keywords must include gas-cap-sensitive outputs (gas rate, gas-oil contact movements via zonal pressures/contacts).
2.3 Water-drive (OIL/gas + water)
Decks that represent aquifer or water influx (edge-drive / bottom-water).[darts.citg.tudelft]
Deck rules:
•	RUNSPEC: OIL, GAS, WATER enabled.
•	PROPS: Aquifer keywords or connection to water influx region (depending on deck style).
•	SCHEDULE: Injectors or aquifer parameters must be supported; avoid vendor-specific aquifer keywords not documented in Flow.[opm-project]
Calling Flow:
•	flow CASE.DATA with summary requests for BHP, water production, field pressure, water cut (FWCT).[pkirkham.github]
•	For MPI: mpirun -np 8 flow CASE.DATA --output-dir=RESULTS and validate water-drive behavior in ResInsight.[resinsight]
2.4 Combination drive
Combination decks mix solution gas, gas cap, and water influx.[darts.citg.tudelft]
Deck rules:
•	PROPS must consistently represent both gas and water drives; avoid mixing incompatible aquifer models and capillary entries.
•	SUMMARY must include combined diagnostics: GOR, FWCT, BHP, reservoir pressure.
Calling Flow:
•	Same CLI; focus is on cleaning unsupported keywords and verifying all relevant SUMMARY vectors exist for later plotting.[opm-project]
2.5 Gravity drainage
Gravity-dominated decks typically emphasize vertical heterogeneity and high density contrasts.[darts.citg.tudelft]
Deck rules:
•	GRID: Fine vertical discretization; gravity terms active.
•	PROPS: Density differences (oil/gas/water) tuned to highlight gravity segregation.
•	SCHEDULE: Minimal external drive; results are dominated by gravity segregation and internal GOR behavior.
Calling Flow:
•	flow CASE.DATA; then inspect vertical profiles (e.g. layer pressures, saturations) via ResInsight.[resinsight]
 
3. IOR and EOR decks
These are “one step beyond primary drive”; Flow supports many but not all Eclipse EOR options.[opm-project]
3.1 IOR (e.g., waterflood)
Waterflood decks: injectors + producers in black-oil settings.[pkirkham.github]
Deck rules:
•	SCHEDULE: WCONINJE, WCONPROD, flood pattern defined in SCHEDULE.
•	SUMMARY: Request recovery efficiency vectors (FOPT, FOIP, FWIT, etc.).
Calling Flow:
•	flow WATERFLOOD.DATA or MPI variant.[pkirkham.github]
•	Use reference waterflood examples from opm-tests/opm-data to check keyword correctness.[opm-project]
3.2 EOR (chemical/thermal, miscible)
Flow supports selected Eclipse EOR features; you must stay inside the documented keyword subset.[opm-project]
Deck rules:
•	Only use EOR keywords explicitly listed in the Flow manual; unsupported thermal or chemical keywords must be removed.[opm-project]
•	Validate PVT and relative permeability tables against EOR modes (miscible, polymer, surfactant, etc.) as described in the reference manual.[opm-project]
Calling Flow:
•	Same flow CASE.DATA pattern, but for EOR runs parameters like timesteps, solver tolerances, and controls may need to be tuned as documented in the manual’s EOR chapter.[opm-project]

How to achieve it	Design 8–12 canonical scenario templates from opm-tests base decks: (1) single-well depletion, (2) 5-spot waterflood, (3) line-drive injector-producer, (4) WAG, (5) pressure buildup test, (6) gas cap expansion, (7) CO2 store (bonus), (8) multilayer heterogeneous. Each is a Jinja2 .DATA template. LLM extracts NL input into a ModelSpec Pydantic object with strict field types. Python renders template → linter validates → return or ask user to clarify.
2. Human strength	Designing what goes into each template — what constitutes a "canonical waterflood deck" that teaches the right physics? What simplifications are pedagogically correct vs. misleading? What parameters must the user always provide explicitly (rel-perm, PVT) vs. can be defaulted? Only you know where the line is.
3. AI capability	NL parameter extraction (grid dimensions, fluid API, well count, schedule duration, GOR). Detecting when the user's description is ambiguous and generating the right clarifying question. Suggesting the closest template when input doesn't exactly match any scenario.
4. Collaboration impact	You write one complete, commented Jinja2 template (the waterflood case) as a reference. AI generates the other 7–11 templates by analogy. You QA each template against its opm-tests reference case — if the rendered deck produces the same results, the template is valid. This QA session is the highest-value human touchpoint.

 
Part 4 — Pre-Processing Pipeline (opm_preprocess)
What it does: Handles all inputs before simulation — PVT table generation from correlation (Standing, Vasquez-Beggs, Al-Marhoun), rel-perm tables from Corey/LET endpoint data, simple grid property mapping, and an AI advisor that recommends the right correlation given a fluid description. Output: ready-to-paste PVTO/PVDO/SWOF/SGOF table blocks.
Prerequisites & Tools:
•	numpy, scipy for correlation math
•	pvtpy or fluids Python libraries (existing PVT correlation implementations)
•	LLM for correlation recommendation and explanation
•	opm-common Python API to validate generated PVT tables against OPM's expected format
	
1. How to achieve it	Implement each PVT correlation (Standing for solution GOR, Vasquez-Beggs for FVF, Al-Marhoun for undersaturated oil) as a Python function with clear input/output. Implement Corey and LET rel-perm as functions from endpoint Sw, So, Sg + curvature exponents. Build an AI advisor: given user's API gravity + GOR + reservoir temperature + region, LLM picks the best correlation and explains why. Output formatted PVTO/SWOF tables that paste directly into an OPM deck section.
2. Human strength	Knowing which correlations are appropriate for which geographies and fluid types (Middle East heavy oil vs. North Sea volatile oil vs. Gulf of Mexico condensate). Validating smoothness of generated PVT tables — Bo must be monotonic, Rs must be non-negative. These "does this make physical sense" checks cannot be automated.
3. AI capability	Correlation recommendation from fluid descriptor. Generating educational explanations of what each PVT parameter controls in the simulation. Spotting outlier values in user-provided lab data before fitting.
4. Collaboration impact	This is the best module for a junior contributor. You write the API spec and validation rules; AI + juniors implement the correlation math from the original papers; you QA outputs against published worked examples from Ahmed's Reservoir Engineering Handbook.

 
Part 5 — Post-Processing & ResInsight Bridge (opm_postprocess)
What it does: After Flow finishes, this module reads summary and grid output files, extracts KPIs (UR, WCT onset, plateau duration, sweep efficiency), and drives ResInsight via the rips Python API to generate plots and 3D views programmatically. No custom rendering code — ResInsight does all the heavy lifting.
Prerequisites & Tools:
•	rips Python package (pip install rips) — ResInsight's gRPC Python client[2]
•	ResInsight ≥ 2025.04 installed (from Ubuntu PPA)[5]
•	python3-opm-common for binary output reading (fallback/KPI extraction)
•	ecl2df (Equinor's Eclipse dataframe library) for summary vector → pandas DataFrame
	
1. How to achieve it	Use rips to: load a completed OPM case, trigger summary plots (WOPR, WWCT, BHP), generate 3D saturation/pressure snapshots at user-specified timesteps, export PNG/HTML. Read summary vectors via ecl2df into pandas to compute KPIs. The AI narration module (Part 7) receives these KPIs as structured data and generates the "what happened" explanation.
2. Human strength	Deciding the canonical plot set that every simulation result should produce. Only a reservoir engineer knows that "recovery efficiency vs. PV injected" is the first plot a waterflood engineer checks — ResInsight won't show this automatically. You define the required KPI list and diagnostic plot set.
3. AI capability	Generating the "result narrator" text from KPI values — "Your WCT broke through at year 3.2, earlier than expected for this kv/kh ratio. This suggests channelling or high permeability streaks." Suggesting follow-up sensitivity runs.
